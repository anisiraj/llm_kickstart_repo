PyTorch Core
Tensors · Autograd · Models · Training loop

PyTorch is the foundation everything else is built on. Before loading any model you need to understand how tensors move between devices, how autograd tracks gradients, and how a training loop ties loss, backprop, and optimizer step together. These patterns repeat verbatim inside every Trainer you'll ever use.

🔷 Tensors & Device

LoRA & QLoRA Concepts
Parameter-efficient fine-tuning — the theory you need

LoRA (Hu et al., 2021) freezes the original weight matrix W and adds a low-rank bypass ΔW = BA (rank r ≪ d). Only A and B are trained — typically 0.1–1% of total parameters — cutting VRAM by 60-80%. QLoRA (Dettmers et al., 2023) goes further: quantise the frozen base to 4-bit NF4, then apply LoRA on top. These two papers made 70B fine-tuning on a single consumer GPU practical.

🧩 What is LoRA?
Freeze the base model. Inject small rank-r matrices (A and B) into attention layers.

Original weight W stays frozen.
Update: ΔW = A × B (r ≪ d)

Only A and B are trained → <1% of total params.

r (rank) = adapter size. Higher r = more expressiveness, more VRAM.
lora_alpha = scaling factor. Keep = r for simplicity.
rsLoRA (use_rslora=True) scales alpha by √r instead of r — better gradient flow at high ranks.
🔢 QLoRA = LoRA + 4-bit
Base model quantized to 4-bit NF4 (NormalFloat4).
LoRA adapters trained in bf16.

Result:
• 8B model: ~16GB → ~5.4GB
• Enables fine-tuning on single consumer GPU

Trade-off: ~39% slower than full LoRA.

When done, merge adapters back into base for inference — no overhead at runtime.
4-bit training = QLoRA. load_in_4bit=True in from_pretrained.

Unsloth — Fast SFT Fine-Tuning
2× faster · 60% less VRAM · Full end-to-end workflow

Unsloth re-implements the hot kernels (RoPE, attention, cross-entropy) in Triton and patches them into Hugging Face models at load time — no model changes required. The result is ~2× faster training and ~60% less VRAM versus a plain PEFT/QLoRA setup. It's the go-to choice for supervised fine-tuning on a single GPU with limited memory.

① Load + ② Attach LoRA
from unsloth import FastLanguageModel

model, tokenizer = FastLanguageModel.from_pretrained(
    model_name    = "unsloth/Meta-Llama-3.1-8B-bnb-4bit",
    max_seq_length= 2048,
    load_in_4bit  = True,   # False → 16-bit LoRA
    dtype         = None)

model = FastLanguageModel.get_peft_model(model,
    r=16, lora_alpha=16, lora_dropout=0,
    target_modules=["q_proj","k_proj","v_proj","o_proj",
                    "gate_proj","up_proj","down_proj"],
    use_rslora=True,
    use_gradient_checkpointing="unsloth")

Causal LM Fine-Tuning & Continued Pretraining
Raw text training · next-token prediction · domain adaptation

Causal language modelling trains the model to predict the next token from raw text — no labels needed. It's the right approach when you want to adapt the model's knowledge or writing style rather than teach it a specific instruction format. Continued pretraining on domain text (medical, legal, code) shifts the model's priors before you apply SFT on top. DataCollatorForLanguageModeling(mlm=False) auto-constructs the shifted labels from your input tokens.

📖 Causal LM Fine-Tuning — What & When
SFT (instruction) = model learns Q→A pairs with chat template.
Causal LM FT = model learns to continue raw text — next-token prediction on your corpus.

Use causal LM fine-tuning when:
  • You want domain-style text generation (legal, medical, code)
  • Your data is raw documents, not instruction pairs
  • You're doing continued pretraining on a new corpus
  • Building a base model before instruction tuning
Key: labels = input_ids — the model predicts every next token. Loss is computed on all tokens (unlike SFT where you can mask the prompt).
🔁 Causal LM Fine-Tune — Full Example
from transformers import (AutoModelForCausalLM, AutoTokenizer,
    Trainer, TrainingArguments, DataCollatorForLanguageModeling)
from datasets import load_dataset

model_name = "meta-llama/Llama-3.1-8B"   # base, not instruct
tok   = AutoTokenizer.from_pretrained(model_name)
tok.pad_token = tok.eos_token              # required for causal LM
model = AutoModelForCausalLM.from_pretrained(
    model_name, device_map="auto", torch_dtype="auto")

# Load raw text corpus
ds = load_dataset("text", data_files={"train":"corpus.txt"})
# or from Hub: load_dataset("wikitext","wikitext-103-raw-v1")

def tokenize(batch):
    enc = tok(batch["text"], truncation=True,
               max_length=2048, padding="max_length")
    enc["labels"] = enc["input_ids"].copy()  # ← predict every token
    return enc

ds = ds.map(tokenize, batched=True, remove_columns=["text"])

# DataCollator handles labels automatically
collator = DataCollatorForLanguageModeling(
    tokenizer=tok, mlm=False)  # mlm=False → causal (GPT-style)

trainer = Trainer(
    model=model,
    args=TrainingArguments(
        output_dir="./causal-ft",
        num_train_epochs=1,
        per_device_train_batch_size=4,
        gradient_accumulation_steps=8,   # eff. batch = 32
        learning_rate=2e-5,
        lr_scheduler_type="cosine",
        warmup_ratio=0.05,
        fp16=True,
        logging_steps=50,
        save_strategy="epoch",
    ),
    train_dataset=ds["train"],
    data_collator=collator,
)
trainer.train()
model.save_pretrained("./causal-ft")

Fine-Tuning Methods — Full Comparison
SFT · Causal LM · DPO · ORPO · GRPO · Pretraining — know which to reach for

Choosing the wrong training method wastes GPU hours. SFT teaches format; Causal LM teaches domain knowledge; DPO / ORPO align the model to human preferences without a live reward model; GRPO uses verifiable rewards (math answers, code execution) for self-improvement. The table below shows exactly when each method applies and what data it needs.

📊 Method Comparison at a Glance
MethodData formatLoss targetWhen to useTRL class
Continued Pretraining Raw text documents All tokens (CLM) Inject domain knowledge into base model SFTTrainer (no template)
Causal LM FT Raw text / completions All tokens (CLM) Style/domain adaptation, base model training Trainer + DataCollatorForLanguageModeling
SFT (instruction) {instruction, response} pairs All or response-only tokens Teach model to follow instructions SFTTrainer
DPO {prompt, chosen, rejected} triples Preference margin loss Align after SFT — prefer chosen over rejected DPOTrainer
ORPO {prompt, chosen, rejected} triples SFT loss + odds ratio penalty SFT + alignment in one pass, no reference model ORPOTrainer
GRPO Prompts + reward function Group relative policy reward Reasoning / math — reward-based RL (DeepSeek-R1 style) GRPOTrainer

🟠 GRPO — RL from Reward (DeepSeek-R1 style)
# GRPO = model generates multiple responses per prompt,
# scores them with a reward function, updates policy.
# Used for reasoning / math / verifiable tasks.
from trl import GRPOTrainer, GRPOConfig

# Define reward function (returns float per response)
def reward_fn(completions, **kwargs):
    # Example: reward correct math answers
    rewards = []
    for c in completions:
        answer = extract_answer(c)   # your parsing logic
        rewards.append(1.0 if answer == correct_answer else 0.0)
    return rewards

ds = load_dataset("openai/gsm8k", "main", split="train")
# gsm8k has "question" column — rename to "prompt" (required by GRPOTrainer)
ds = ds.map(lambda x: {"prompt": x["question"]}, remove_columns=["question"])

trainer = GRPOTrainer(
    model=model,
    reward_funcs=[reward_fn],   # reward_funcs is a LIST of callables
    args=GRPOConfig(
        output_dir="./grpo-out",
        num_train_epochs=1,
        per_device_train_batch_size=4,
        learning_rate=1e-6,
        num_generations=4,            # must be <= per_device_train_batch_size
        max_completion_length=512,    # renamed from max_new_tokens in trl 1.x
        fp16=True,
    ),
    processing_class=tok,
    train_dataset=ds,
)
trainer.train()

📌 Recommended Training Pipeline
For a general assistant:
  1. Start from a strong base model (Llama, Qwen, Mistral)
  2. Optional: Continued pretraining on your domain corpus
  3. SFT on instruction pairs (Unsloth + SFTTrainer)
  4. DPO on preference data to align outputs
For a reasoning / math model:
  1. Start from instruct model
  2. GRPO with verifiable reward (accuracy, format)
For fastest path to aligned model:
  1. Base model → ORPO (SFT + alignment in one shot)
LR guidelines: Pretraining 1e-4 → SFT 3e-4 → DPO 5e-7 → GRPO 1e-6
Always use a lower LR for alignment than for SFT.

The Dataset Zoo
PyTorch Dataset → DataLoader → HF Dataset → DataCollator — untangled

Four things called "dataset" and nobody explains how they connect. This is the single biggest source of confusion when coming from general Python/ML into the HuggingFace fine-tuning stack. Here's the complete picture — what each layer does, when you need it, and what the Trainer hides from you.

🔶 PyTorch Dataset
from torch.utils.data import Dataset

class MyDataset(Dataset):
    def __init__(self, texts, tokenizer):
        self.texts = texts
        self.tokenizer = tokenizer

    def __len__(self):
        return len(self.texts)

    def __getitem__(self, idx):
        return self.tokenizer(self.texts[idx])
What: Abstract base class. You subclass it, implement __len__ + __getitem__.
Storage: Row-oriented, in-memory (everything in RAM).
Use when: Custom data sources, non-text data, legacy code.
For LLM fine-tuning: Almost never needed — HF Dataset replaces this.
🔷 HF datasets.Dataset
from datasets import Dataset, load_dataset

ds = load_dataset("json", data_files="data.jsonl")
ds = Dataset.from_dict({"text": ["hi", "bye"]})

# Transform without subclassing
ds = ds.map(tokenize_fn, batched=True)
ds = ds.filter(lambda x: len(x["text"]) > 10)

# Make it act like a PyTorch Dataset
ds.set_format("torch")
What: Column-oriented, Arrow-backed, memory-mapped from disk.
Storage: Doesn't load everything into RAM. 50GB dataset? No problem.
Has: .map(), .filter(), .select() — no subclassing needed.
Key insight: It implements __getitem__ + __len__, so DataLoader and Trainer accept it directly.
🔀 DataLoader
from torch.utils.data import DataLoader

loader = DataLoader(
    dataset,            # any Dataset (PyTorch or HF)
    batch_size=8,
    shuffle=True,
    num_workers=4,
    collate_fn=collator # ← this is where collators plug in
)

for batch in loader:
    outputs = model(**batch)
What: Wraps a Dataset. Handles batching, shuffling, parallel loading.
collate_fn: Takes a list of individual samples → returns one batch dict.
You rarely create one. Trainer builds it internally from your dataset + collator.
📦 DataCollator
from transformers import (
    DataCollatorWithPadding,          # classification
    DataCollatorForLanguageModeling,  # causal LM / MLM
    DataCollatorForSeq2Seq,           # encoder-decoder
)
from trl import DataCollatorForCompletionOnlyLM # SFT

collator = DataCollatorForLanguageModeling(
    tokenizer=tok, mlm=False)   # causal LM
What: A fancy collate_fn. Takes list of examples → returns padded + labeled batch.
Dynamic padding: Pads to longest in batch, not global max (saves compute).
Creates labels: For causal LM, labels = input_ids with -100 on padding.
Key detail: The label shift for next-token prediction happens inside the model, not in the collator.
⚡ How Trainer Wires It All Together
You provide:                          Trainer creates internally:
─────────────                          ──────────────────────────
train_dataset  (HF Dataset)         →  DataLoader(
  +                                        dataset=train_dataset,
data_collator  (e.g. LM collator)   →      collate_fn=data_collator,
  +                                        batch_size=args.per_device_train_batch_size,
TrainingArguments                    →      sampler=RandomSampler,
                                       )

# The Trainer's default collator selection:
# 1. You provide data_collator           → uses that
# 2. You provide tokenizer, no collator  → DataCollatorWithPadding
# 3. Neither                             → default_data_collator (just stacks)

# SFTTrainer goes even further:
trainer = SFTTrainer(
    model="Qwen/Qwen3-0.6B",
    train_dataset=ds,           # just needs a "text" or "messages" column
    args=SFTConfig(output_dir="./out"),
)
# SFTTrainer handles: tokenization → collation → label masking → training
# You never write a collator or DataLoader.
📋 Which Collator For What?
Collator Task What It Does
DataCollatorWithPadding Classification Dynamic padding only. No label manipulation.
DataCollatorForLanguageModeling Causal LM / MLM mlm=False: labels = input_ids, -100 on padding. mlm=True: masks 15% of tokens.
DataCollatorForSeq2Seq Translation, Summarization Pads both input and decoder labels. -100 on label padding.
DataCollatorForCompletionOnlyLM SFT (instruction tuning) Masks prompt tokens with -100. Only completion contributes to loss.
default_data_collator Pre-padded data Just stacks tensors. No padding. Requires uniform sequence lengths.
⚠️ Common Gotchas
1. "I padded in .map() — why do I need a collator?"
You don't need one, but fixed padding wastes compute. A batch of [12, 18, 15]-token sequences pads to 18, not 512. That's the collator's job.

2. "I wrote a PyTorch Dataset subclass"
You almost certainly didn't need to. Dataset.from_dict() or load_dataset() + .map() covers 99% of fine-tuning.

3. "HF Dataset vs PyTorch Dataset — which am I using?"
They're different classes from different libraries. HF datasets.Dataset is NOT a subclass of torch.utils.data.Dataset. It just implements the same interface (duck typing). Both work with DataLoader.

4. "Where does the label shift happen for next-token prediction?"
Not in the collator. The collator sets labels = input_ids. The one-position shift happens inside model.forward(). The model handles its own architecture.

5. "Loss doesn't decrease despite training"
Check labels. If you set labels manually AND use a LM collator, they may conflict. Let the collator handle labels, or don't use one.

PyTorch Module Internals
nn.Module · ModuleList gotcha · Weight surgery · HF head swapping

PyTorch's module system is deceptively simple — until you store layers in a plain Python list and nothing trains. This chapter covers the mechanics that senior developers trip over: how nn.Module discovers parameters, why nn.ModuleList exists, how to freeze/unfreeze layers, and what HuggingFace actually does when you call AutoModelForSequenceClassification.

⚠️ The ModuleList Gotcha — #1 Silent Bug
# WRONG — layers are INVISIBLE to PyTorch
class BrokenNet(nn.Module):
    def __init__(self):
        super().__init__()
        self.layers = [nn.Linear(10, 10)
                        for _ in range(3)]
        # ↑ plain list: .parameters() returns NOTHING
        # Won't train, won't save, won't move to GPU

# CORRECT — use nn.ModuleList
class FixedNet(nn.Module):
    def __init__(self):
        super().__init__()
        self.layers = nn.ModuleList([
            nn.Linear(10, 10) for _ in range(3)
        ])
        # ↑ registered! .parameters() finds all 6 tensors

# Same for dicts: use nn.ModuleDict, not {}
self.heads = nn.ModuleDict({
    "cls": nn.Linear(10, 2),
    "reg": nn.Linear(10, 1),
})
Rule: If it has parameters, it must be an nn.Module attribute — not inside a plain Python list or dict.
🔀 Non-Linear Forward Pass
class ResidualBlock(nn.Module):
    def __init__(self, dim):
        super().__init__()
        self.ff = nn.Sequential(
            nn.Linear(dim, dim * 4),
            nn.GELU(),
            nn.Linear(dim * 4, dim),
        )
        self.norm = nn.LayerNorm(dim)

    def forward(self, x):
        return self.norm(x + self.ff(x))
        # ↑ skip connection: input goes TWO paths

# Multi-head: shared backbone, different task heads
class MultiTaskModel(nn.Module):
    def forward(self, x, task="cls"):
        features = self.backbone(x)  # shared
        if task == "cls":
            return self.classifier(features)
        return self.regressor(features)
forward() is just Python. Skip connections, branches, conditionals, shared layers — all fine. nn.Sequential is a convenience, not a requirement.

Adapter Patterns — Save, Load, Swap
One base model · Many specialists · Hub integration · Merge for deploy
Why Adapters Matter
A LoRA adapter is ~1% the size of the base model. Save it, share it, swap it — without duplicating the base weights.

Base model (~500 MB) + 10 adapters (~10 MB) = 10 specialized models

This is how production systems work: one base loaded in memory, adapters hot-swapped per request.
Save & Reload
Save — only adapter weights, not the full model:
model.save_pretrained("./my-adapter/")

Creates just two files: adapter_config.json (~1 KB) + adapter_model.safetensors (~MB).

Reload onto a fresh base:
PeftModel.from_pretrained(base, "./my-adapter/")

Gotcha: Use PeftModel.from_pretrained() to load. get_peft_model() is for creating a new adapter.
Merge for Deployment
Bake adapter weights into the base model — no PEFT dependency at inference:
model = model.merge_and_unload()

Result: a plain transformers model. Ship it, export to GGUF, deploy anywhere.

Gotcha: merge_and_unload() is not in-place. You must assign the return value.

Trade-off: merged model = full size again. Can't swap adapters anymore.
HuggingFace Hub
Adapters live on the Hub just like full models. Push ~5 MB instead of ~5 GB:
model.push_to_hub("my-org/hvac-adapter")

Pull from anywhere:
PeftModel.from_pretrained(base, "my-org/hvac-adapter")

Or auto-detect the base model:
AutoPeftModelForCausalLM.from_pretrained("my-org/hvac-adapter")

Real example: ybelkada/opt-350m-lora — a 6 MB adapter for OPT-350M.
Multi-Adapter Swap
Load multiple adapters onto one base model and switch per request:

model = PeftModel.from_pretrained(base, path_a, adapter_name="hvac")
model.load_adapter(path_b, adapter_name="energy")
model.set_adapter("hvac")   # → HVAC specialist
model.set_adapter("energy") # → energy specialist

Gotcha: load_adapter() does not activate the adapter. Always call set_adapter() after loading.

One base model + named adapters = an organizational knowledge registry. Each adapter encodes domain expertise that lives independently — versioned, auditable, swappable.

How to Know If Fine-Tuning Worked
Loss curves · Perplexity · Generation quality · Overfitting detection

Fine-tuning without evaluation is flying blind. You need to check at least three things: is the loss decreasing?, is the model generating better outputs?, and is it overfitting? This section gives you the concrete patterns.

📉 1. Loss Curves
# After trainer.train(), inspect the log history
result = trainer.train()

for entry in trainer.state.log_history:
    if "loss" in entry and "eval_loss" not in entry:
        print(f"step {entry['step']:>4d}  loss={entry['loss']:.4f}")
    if "eval_loss" in entry:
        print(f"epoch {entry['epoch']}  eval_loss={entry['eval_loss']:.4f}")
Train loss should decrease steadily. If eval loss spikes while train loss drops — you're overfitting.
📐 2. Perplexity
import math

# Perplexity = exp(eval_loss)
# Lower = model assigns higher probability to correct tokens
metrics = trainer.evaluate()
ppl = math.exp(metrics["eval_loss"])
print(f"perplexity: {ppl:.2f}")

# Compare before vs after fine-tuning
# baseline_ppl=328 → after_ppl=9 = significant improvement
Perplexity is the standard LM metric. Always compute it before AND after fine-tuning to measure improvement.
🔍 3. Generation Quality Check
# Use the same prompts before and after training
test_prompts = ["LoRA injects", "The learning rate", "GRPO uses"]

for prompt in test_prompts:
    inputs = tok(prompt, return_tensors="pt").to(device)
    with torch.no_grad():
        out = model.generate(**inputs, max_new_tokens=40, temperature=0.7)
    print(tok.decode(out[0], skip_special_tokens=True))

# BEFORE: "LoRA injects a new layer of complexity into the game..."  (generic)
# AFTER:  "LoRA injects low-rank matrices into transformer..."       (domain-relevant)
Automated metrics don't catch everything. Always eyeball generations from a fixed set of test prompts.
⚠️ 4. Overfitting Detection
Symptom: train_loss keeps dropping, but eval_loss starts rising after epoch N.
Cause: Model is memorizing training examples instead of learning patterns.
Fixes:
  • Reduce num_train_epochs (often 1–3 is enough for fine-tuning)
  • Add more training data
  • Increase weight_decay (e.g., 0.01 → 0.1)
  • Use eval_strategy="steps" with small eval_steps to catch the turn early
Always pass an eval_dataset to the trainer. Without it, you have no way to detect overfitting.
⚠️ 5. The metric format-trap — when perplexity LIES
The single most expensive evaluation mistake: judging an instruction model with a raw-text metric. An SFT'd model "wants" chat tokens, so on plain text it looks worse — even when it's far better at the actual task. SFT can raise domain perplexity while completion perplexity collapses, because the two losses pull in opposite directions. 
# MiniCPM5-1B, measured before/after SFT (case study §6):
#   completion ppl  107.68 -> 3.64   (-97%)   ← SFT's real job, huge win
#   domain ppl       24.81 -> 34.90   (+41%)  ← rose! raw-text metric is misleading here
#   keyword recall      5% -> 46%     (9x)    ← format-robust, confirms the win
Rule: match the metric to the phase. Judge CPT by domain perplexity; judge SFT by completion perplexity and a generation-based metric (keyword recall / ROUGE) that doesn't punish format. Never rank a base-vs-instruct decision on one perplexity number. Full metric playbook: Metrics cheatsheet.
See it in action: scripts/10_evaluation.py runs a full before/after comparison — loss tracking, perplexity measurement, generation quality checks — all in one script. The format-trap is measured live in the 🧪 Case Study (case_study/scripts/07_eval.py).

Loss Masking, Chat Templates & Learning Rates
The SFT mechanics that decide whether training learns the right thing

Three knobs quietly decide the fate of an SFT run: which tokens carry the loss, which chat template wraps them, and what learning rate moves which weights. Get them wrong and the loss still goes down — you've just taught the wrong thing. Quick reference: SFT Trainer cheatsheet · Chat Templates cheatsheet. 🧪 Runnable: scripts/05_sft.py trains with completion-only loss and prints the unmasked fraction (measured 78–81%).

🎯 The 3 loss modes
ModeLoss onFor
full causalevery tokenCPT / raw text
completion-onlyanswer (prompt masked)SFT Q&A
assistant-onlyassistant turnsmulti-turn chat
"Masking" = setting masked labels to -100 so CrossEntropyLoss(ignore_index=-100) skips them. It's the loss that's masked, not attention.
💬 The chat template IS the mask boundary
# completion-only loss finds the boundary from the template:
# <|im_start|>user … <|im_end|>          ← masked (-100)
# <|im_start|>assistant  ANSWER <|im_end|> ← learned
text = tok.apply_chat_template(msgs, tokenize=False,
                                  add_generation_prompt=False)
Forget the mask and the model learns to generate the question too → at inference it "echoes the prompt back." The classic SFT bug.
📈 Learning rates that work
WhatLRWhy
LoRA adapters1e-4 – 3e-4tiny matrices tolerate a high LR
embeddings / lm_head~5e-6huge layers → small steps or they destabilize
full fine-tune1e-5 – 5e-5all weights move
Use warmup_ratio≈0.03 + a cosine schedule. Unsloth supports a separate embedding_learning_rate for the CPT case.
✅ Prove the mask (one line)
lab = next(iter(trainer.get_train_dataloader()))["labels"]
print((lab != -100).float().mean())
# CPT  → 1.00 (nothing masked)
# SFT  → 0.78–0.81 (prompt masked)   ← measured in the case study
If your SFT number is 1.0, the prompt isn't masked. Catch it in seconds, not after a wasted run.

Tokenizer & Vocabulary Surgery
Extra tokens, embedding resizing, and when to retrain the embeddings

Adding tokens and training embeddings is powerful and easy to get wrong. The honest default is you probably don't need new tokens — and when you do, there's an exact ritual. Reference: Chat Templates & Data Prep cheatsheet. 🧪 Runnable: scripts/18_token_surgery.py verifies every step on SmolLM2-135M — measured: LaTeX→11 tokens, JSON→9 (no surgery needed), and a new token's embedding row lands 0.0001 from the pretrained mean (vs 2.36 average spread).

🧪 First: do you even need them?
# Check what the tokenizer already does with your content
len(tok(r"$\hat{H}\psi=E\psi$").input_ids)   # LaTeX = ASCII → fine
len(tok('{"k": 1}').input_ids)             # JSON = ASCII → fine
LaTeX, JSON, HTML, code and chemical formulae are plain ASCII — BPE handles them. Adding tokens you don't need just dilutes training signal.
➕ Adding tokens correctly
tok.add_special_tokens(
   {"additional_special_tokens": ["<rxn>", "</rxn>"]})
model.resize_token_embeddings(len(tok),
                            mean_resizing=True)   # init at embedding mean
mean_resizing=True puts new rows on the pretrained manifold (far better than random). It's simple but collapses many new tokens into one subspace — fine for a few control tokens, risky for hundreds.
🧠 Retraining the embeddings
# Add embed_tokens + lm_head to LoRA targets ONLY when:
#  • CPT shifts the token distribution a lot, OR
#  • you added new tokens (their rows start near-random)
target_modules += ["embed_tokens", "lm_head"]
embedding_learning_rate = 5e-6   # < base LR, or they destabilize
Connects to the LR chapter: big layers want a small LR. New rows must be trained or they stay meaningless.
⚠️ The cost (when NOT to)
Targeting embed_tokens+lm_head on a 3B blew the adapter from 116 MB → 1.2 GB (measured). On tiny SFT data over existing tokens it also overfits.
For plain SFT on existing tokens: leave embeddings out. Train them for CPT or genuinely new vocabulary — not by default.

Catastrophic Forgetting
When teaching the new makes it forget the old — detect it, then prevent it

Fine-tuning can quietly erode general ability while it learns your domain. The good news: with LoRA it's rare, and it's trivial to measure so you never ship it blind. Seen in the 🧪 Case Study (we checked, and didn't forget). 🧪 Runnable: scripts/04_cpt_base_vs_instruct.py measures domain vs general perplexity before/after CPT.

🔬 Detect it (cheap)
# perplexity on GENERAL text, before AND after training
gen_before = perplexity(model0, tok, general_text)
gen_after  = perplexity(model1, tok, general_text)
# rising general PPL = forgetting
# measured (SmolLM3-3B): 8.33 → 8.19  → NO forgetting
Always hold out a small general-text set and check it alongside your domain metric. One number tells you if you broke the base.
🛡️ Why LoRA helps
The base weights are frozen; only small adapters move. You can even remove the adapter to recover the original model exactly. Full fine-tuning has no such safety net — every weight drifts.
🧯 Mitigate it
• Fewer epochs / lower LR — most forgetting comes from over-training on a narrow set.
• Replay / data mixing — blend a little general instruction data into your domain set.
• Keep LoRA rank modest — huge adapters on tiny data overfit (and overwrite more).
• Adapter isolation — keep domain skills in separate adapters, swap at inference (see Adapter Patterns) instead of one over-trained model.

What I built, on what hardware
The goal: ask "What is the Hartree–Fock method?" and get a correct, concise answer from a model small enough to run at the edge. I ran the same pipeline on three Apache-2.0 models so you can see how size changes the story — swapping models is one variable (config.py), so bash run.sh minicpm5 vs smollm3 is the only change:
  • SmolLM2-135M — the floor. Shows the mechanics; too small to give real answers (you'll see it fail, on purpose).
  • SmolLM3-3B — capable: real answers and reasoning, but a newer architecture that complicates deployment.
  • MiniCPM5-1B — my favourite here: small and tool-capable, Llama-architecture (deploys trivially), and it gave the most dramatic before/after of the three.
Everything below ran on one RTX 3080 Ti (12 GB). The 3B fits via QLoRA (4-bit). Your numbers will differ a little with seed/hardware — that's expected, and it's why I report direction and relative change, never leaderboard scores.
The one idea to hold onto: two phases, two different losses
A model that "knows chemistry" and a model that "answers chemistry questions" are two different things, taught in two phases. This single table is the spine of the chapter:
CPT — Continued PreTrainingSFT — Supervised Fine-Tuning
teachesthe domain (knowledge, vocabulary, notation)the task (follow an instruction, answer a question)
dataraw text (Wikipedia articles)prompt → completion pairs (Q&A)
loss computed on…every token (full causal LM)only the answer (the prompt is masked)
data abundanceplentiful — you scrape itscarce — you hand-write it
what movesdomain perplexity ↓completion perplexity ↓, answer recall ↑
Everything that follows is me proving each row in code and numbers. The "loss computed on…" row is the one beginners get wrong, so I prove it twice (Steps 4 and 5) by literally counting masked tokens.
Step 1 — Build the corpus (and survive the equations)
I pulled ~40 chemistry pages from Wikipedia through the MediaWiki API. Two things bit me, so the code handles both up front:
  1. You must send a User-Agent — Wikipedia returns HTTP 403 to anonymous scrapers. Cost me ten confused minutes the first time.
  2. Equations come out twice — once as a broken glyph-by-glyph dump, once as clean LaTeX inside {\displaystyle …}. Feed the glyph soup to training and you're literally teaching the model noise.
import urllib.request, urllib.parse, json

UA = "chem-corpus/0.1 (educational; you@example.com)"   # required, or you get 403

def fetch_plaintext(title):
    p = dict(action="query", format="json", prop="extracts",
             explaintext=1, redirects=1, titles=title)
    url = "https://en.wikipedia.org/w/api.php?" + urllib.parse.urlencode(p)
    req = urllib.request.Request(url, headers={"User-Agent": UA})
    page = next(iter(json.load(urllib.request.urlopen(req))["query"]["pages"].values()))
    return page["extract"]

# Keep the LaTeX, drop the glyph-soup duplicate. Balanced-brace scan because LaTeX
# nests {…}, so a greedy/non-greedy regex would truncate the formula mid-expression.
def extract_math(text):
    out, i = [], 0
    while (j := text.find("{\\displaystyle", i)) != -1:
        out.append(text[i:j])                       # text before the formula
        depth, k = 0, j
        while k < len(text):                    # walk to the matching close brace
            depth += (text[k] == "{") - (text[k] == "}")
            if depth == 0: break
            k += 1
        latex = text[j+len("{\\displaystyle"):k].strip()
        out.append(f" $ {latex} $ ")             # keep it as inline $LaTeX$
        i = k + 1
    return "".join(out)
I also NFKC-normalize, strip boilerplate (References / See also), and deduplicate by content hash — Wikipedia redirects silently point several titles at the same article, which would over-weight those topics.
Measured result: 41 unique pages, ~111,956 tokens, 1,149 equations preserved as inline $LaTeX$ — and I added no new tokens (LaTeX is plain ASCII; the existing tokenizer handles it fine). Full code: scripts/01_build_corpus.py.
Step 2 — The reality that shapes every later decision: instruction data is scarce
Raw text was nearly free — a few dozen pages gave ~112k tokens in seconds. Instruction pairs are not: someone has to write the answers. Here's the unit of SFT data, and how few I actually had: 
# One prompt → completion pair. I hand-wrote 32 of these, by hand, one at a time.
{"prompt": "What does the Hartree-Fock method approximate?",
 "completion": "It approximates the many-electron wavefunction as a single "
               "Slater determinant and treats electron repulsion in a mean-field way."}
The asymmetry that decides everything: ~112,000 corpus tokens vs ~1,132 tokens of hand-written Q&A — a ~99× gap. This is the real reason "just fine-tune it" is harder than it sounds, and it's why Step 7 (base vs instruct init) matters so much: with this little SFT data, your starting point dominates the outcome. Step 3 — Chat templates: what the model actually reads (and why it matters twice)
My data is just {"prompt":…, "completion":…}. But an instruction-tuned model was never trained on bare text — it was trained on conversations wrapped in special role tokens. Before training (and again at inference), the tokenizer's chat template converts a message list into exactly that format. You have to see what it produces: 
msgs = [{"role": "user", "content": "What is the Hartree-Fock method?"}]
text = tok.apply_chat_template(msgs, tokenize=False, add_generation_prompt=True)
print(text)
# <|im_start|>user                              ← ChatML role tokens, baked into THIS model
# What is the Hartree-Fock method?<|im_end|>
# <|im_start|>assistant                         ← add_generation_prompt=True adds this open turn;
#                                                 the model writes its answer right after it
Three things to internalize, because they connect training and deployment:
  • The template is model-specific. SmolLM/MiniCPM use ChatML (<|im_start|>…<|im_end|>); Llama-3 and Mistral use different tokens. Never hardcode — read tok.chat_template or use Unsloth's get_chat_template(tok, "chatml") (see the Unsloth/LoRA cheatsheet).
  • It's what lets completion-only loss find the boundary. The mask in Step 5 keys off "everything up to <|im_start|>assistant is the prompt → set to -100; the assistant's tokens are the answer → learn those."
  • The same <|im_end|> token reappears at deploy time — my Ollama Modelfile sets stop "<|im_end|>" so the server knows when the answer is finished. One token ties the whole pipeline together.
For a base (non-instruct) model there is no chat template — you feed raw text and let it continue. That's exactly why, in my eval code, generate_samples(..., chat=False) for base/CPT models and chat=True for instruct/SFT models. Mixing those up is a subtle, silent cause of "why are my answers garbage." Code: scripts/utils.py:generate_samples.
Step 4 — CPT: teach the domain (loss on every token)
CPT is just "keep pretraining" on my domain text: predict the next token, over and over. I don't update the whole model — that needs too much memory — I use QLoRA: load in 4-bit, freeze it, train tiny low-rank LoRA adapters. Three choices that matter:
  • rank r + use_rslora: the adapter's capacity. rank-stabilized LoRA scales the update by α/√r (not α/r) so high ranks stay stable. Step 8 sweeps this — with a result that surprised me.
  • I add embed_tokens + lm_head to the targets (CPT only): CPT shifts the token distribution (lots of math/LaTeX), so the embedding layers need to adapt — at a smaller learning rate (5e-6) so they don't destabilize.
  • packing: glue documents together (EOS-separated), cut into fixed 512/1024-token blocks — no wasted padding.
from unsloth import FastLanguageModel

model, tok = FastLanguageModel.from_pretrained(
    "HuggingFaceTB/SmolLM3-3B-Base", max_seq_length=512, load_in_4bit=True)  # QLoRA

model = FastLanguageModel.get_peft_model(model,
    r=32, lora_alpha=32, use_rslora=True,            # high rank, rank-stabilized
    target_modules=["q_proj","k_proj","v_proj","o_proj",
                    "gate_proj","up_proj","down_proj",
                    "embed_tokens", "lm_head"])             # ← CPT adapts embeddings too

# Pack the corpus into fixed blocks; labels == input_ids ⇒ predict EVERY token.
blocks  = pack_documents(tok, corpus_texts, block_size=512)
dataset = Dataset.from_dict({"input_ids": blocks, "labels": [b[:] for b in blocks]})

# PROOF the loss is full: count labels that aren't masked (-100).
lab = dataset[0]["labels"]
print(f"unmasked: {sum(x != -100 for x in lab) / len(lab):.0%}")   # → 100%  (nothing masked)
Measured (SmolLM3-3B): held-out domain perplexity 11.19 → 11.15 (−0.3%). Honestly? Tiny. I expected more — but a 3B already knows textbook chemistry, so there's little left to teach from 40 articles. The general lesson is real and worth stating plainly: CPT pays off on a weak base or genuinely novel notation, not on a strong model that already saw the domain. (I also checked for catastrophic forgetting — general-text perplexity went 8.33 → 8.19, so it didn't forget.) Code: scripts/03_cpt.py (HF + Unsloth backends).
Step 5 — SFT: teach the task (loss on the answer only)
Now I teach it to answer. Same LoRA idea, two differences from CPT: the data is prompt→completion, and loss is computed on the completion only — the prompt tokens become -100 (ignored). That single flag is the entire difference between "learn everything" and "learn only the answer": 
from trl import SFTConfig, SFTTrainer

trainer = SFTTrainer(
    model=model, train_dataset=qa_pairs, processing_class=tok,
    args=SFTConfig(
        completion_only_loss=True,       # ← THE line: mask the prompt, learn only the answer
        num_train_epochs=3, learning_rate=2e-4, packing=False))   # no packing keeps the mask clean

# PROOF the mask is on: pull one real collated batch and count non-(-100) labels.
labels = next(iter(trainer.get_train_dataloader()))["labels"]
print(f"unmasked: {(labels != -100).float().mean():.0%}")   # → ~78–81% (the prompt is masked!)
Put the two proofs next to each other: CPT 100% unmasked, SFT ~80% unmasked. The masked ~20% is the question text — the part we do not want the model learning to generate. Forget completion_only_loss and the model learns to produce questions too; at inference it then "echoes the prompt back" before (or instead of) answering. That's the single most common beginner bug, and now you can detect it in one line.
Measured (MiniCPM5-1B): held-out completion perplexity 107.68 → 3.64 (−97%), and on held-out questions it actually answers — verbatim from my run: "What is the Hartree–Fock method?" → "An approximate wavefunction-based method that approximates the many-electron wavefunction as a single Slater determinant and treats electron–electron repulsion in a mean-field (averaged) way." Code: scripts/05_sft.py.
Step 6 ★ — Base → CPT → SFT: the direction of improvement, measured
This is the comparison the whole chapter exists for. Same model, three states, the metrics that match each phase. Watch which number each phase moves — that's the proof the two phases do two different jobs:

Read the arrows. Recall went 5% → 46% and completion perplexity collapsed 30× — that is not "the base already knew it." On our custom Q&A the base model essentially can't do the task, and the fine-tune clearly can. That's the differentiation, in numbers you can reproduce.
The detail I almost missed — and it's the most instructive one: SFT made domain perplexity go up (24.81 → 34.90) while completion perplexity cratered. The two losses literally pull in opposite directions: SFT tunes the model to answer in our format, which makes it slightly worse at continuing raw prose. So you cannot judge an SFT model with a raw-text (domain) metric — it will look like a regression. Use the metric that matches the phase: completion perplexity and recall for SFT. This is the same trap, from a different angle, that bites the base-vs-instruct experiment in Step 7.
And the qualitative side, the same question after each phase (this is why CPT alone is not enough):

CPT moved domain perplexity; SFT moved completion perplexity and recall. Two phases, two jobs — visible in both the words and the numbers. Step 7 — With little data, start from the instruct model (and don't trust perplexity)
Should I SFT the base model or the already-instruction-tuned one? With ~30 examples it matters a lot. I swept the training-set size for both, and measured two ways on purpose: 
for init in ("base", "instruct"):
    for n in [4, 8, 16, 24]:                 # vary how many Q&A pairs
        m = sft(init, train_pairs[:n])
        ppl    = completion_perplexity(m, heldout)   # format-sensitive — can lie
        recall = keyword_recall(m, heldout)          # generation-based — format-robust
The trap I walked into: by perplexity, "base wins." But that's a format artifact — the chat-tuned instruct model is penalized when scored on plain text (the same effect as Step 6's rising domain ppl). Score by keyword recall — what fraction of the right answer it actually generates — and the real story flips:
SmolLM3-3B, recall as N grows 4 → 24base initinstruct init
keyword recall16% → 6% (destabilizes)16% → 21% (improves with data)
Two lessons for the price of one: with scarce data, instruct-init wins and scales with data while base-init falls apart — and pick the metric that matches the task, or perplexity will quietly lie to you. Code: scripts/06_base_vs_instruct_sweep.py.

Step 9 ★ — Ship it: a sub-1 GB model serving on your own machine (every command)
A fine-tune is useless if you can't run it. This is the full, no-hand-waving path — exactly the commands I ran. The flow: merge the LoRA into the base → (if needed) convert to GGUF → let Ollama quantize to Q4_K_M and serve a local API.

1. Merge the adapter into standalone weights (adapters can't be converted or served on their own):

from transformers import AutoModelForCausalLM, AutoTokenizer
from peft import PeftModel

base   = AutoModelForCausalLM.from_pretrained("openbmb/MiniCPM5-1B-sft", torch_dtype="bfloat16")
merged = PeftModel.from_pretrained(base, "outputs/sft_instruct_full").merge_and_unload()
merged.save_pretrained("outputs/merged_full", safe_serialization=True)
AutoTokenizer.from_pretrained("openbmb/MiniCPM5-1B-sft").save_pretrained("outputs/merged_full")

2. Architecture decides your next step. MiniCPM5 is Llama-architecture, so Ollama imports the safetensors directly — skip to step 3. SmolLM3 is a newer arch (SmolLM3ForCausalLM) Ollama can't read as safetensors, so it needs a GGUF first (no compile required):

# SmolLM3 only — produce an F16 GGUF; Ollama quantizes it in step 3
python llama.cpp/convert_hf_to_gguf.py outputs/merged_full \
       --outfile outputs/merged_full/model-f16.gguf --outtype f16

3. Write a Modelfile (this is the real one my script emits — note stop "<|im_end|>", the same ChatML token from Step 3):

FROM .                                  # MiniCPM5: the merged dir. SmolLM3: ./model-f16.gguf
PARAMETER temperature 0.3
PARAMETER num_ctx 2048
PARAMETER stop "<|im_end|>"
SYSTEM "You are a concise assistant for computational and quantum chemistry."

4. Import + quantize to Q4_K_M, then run it — Ollama does the quantization on import:

cd outputs/merged_full
ollama create chem-minicpm5 -q q4_K_M -f Modelfile
ollama run chem-minicpm5 "What is the Hartree-Fock method?"

5. Or serve it to a harness over Ollama's local REST API (OpenAI-compatible at /v1/chat/completions); the timings field is how you measure tok/s:

curl localhost:11434/api/generate -d '{
  "model":"chem-minicpm5",
  "prompt":"What does the Hartree-Fock method approximate?",
  "stream":false, "options":{"temperature":0.3,"num_predict":64}}'
# → {"response":"It approximates the many-electron wavefunction ...",
#    "eval_count":58, "eval_duration":...}   # tok/s = eval_count / (eval_duration/1e9)
Measured, deployed (SmolLM3-3B via Ollama, RTX 3080 Ti): 1.915 GB on disk at Q4_K_M, serving at ~242 tok/s (per-query 230–250 across six held-out questions of 20–55 tokens — taken from the API's eval_count/eval_duration, not a stopwatch). A real deployed answer: "What is the Hartree–Fock method?" → "A self-consistent approximation that … expanding the many-electron wavefunction as a Slater determinant and solving for orbitals to minimize energy." MiniCPM5-1B is smaller still at 0.689 GB. Code: scripts/09_merge_and_gguf.py, scripts/10_ollama_deploy.py, scripts/11_edge_benchmark.py.
One honest gotcha worth keeping: the separate §11 edge-benchmark script — which calls the model's own generate() rather than the Ollama API — returned a degenerate 1-token result on its probe prompt: an under-trained 32-pair model sometimes emits the end-of-turn token immediately. The lesson is about where you measure: time tok/s on a normal-length answer (the Ollama API path above gives a clean, consistent number), and never trust a single short generation. §11 documents taking the same eval_count/eval_duration metric on a Raspberry-Pi-class device.
Step 10 — What fine-tuning can't buy you: size vs capability
Identical recipe, three sizes, and the gap is all about size: the fine-tuned 135M produces gibberish, the 1B and 3B answer in clean prose, and only the larger two reliably tool-call. Fine-tuning teaches a task on top of a capability the base already has — it does not conjure a capability from nothing.

And I'll keep myself honest: the 1B answers are well-formed but not always correct. Real outputs from my run — a good one and a wrong one, side by side:

MiniCPM5-1B answer (verbatim)verdict
"MCSCF: multi-configurational self-consistent field — it optimizes both the orbitals and the coefficients of several determinants, important when static correlation is strong."correct
"[one-electron density matrix is] an operator that gives the density of the system; its eigenvalues are the energies."wrong — confidently
This is the real takeaway of the whole case study: at 1B you get a fluent, on-format domain assistant that runs in 0.7 GB — fantastic for drafting and recall, but it still hallucinates, so keep a human (or a retrieval/verification layer) in the loop. That trade-off, made with eyes open, is exactly why MiniCPM5-1B is the interesting size: small enough for the edge, big enough to be useful, honest enough to need supervision. Why two virtual environments?

Unsloth hard-pins trl<0.9.0 in its dependencies. The DPO, ORPO, and GRPO trainers require trl≥1.0 — a completely different API with renamed parameters (max_completion_length, processing_class, etc.) and new trainer classes. These two constraints are mutually exclusive: pip cannot satisfy both in the same environment, and installing one silently downgrades or breaks the other.
