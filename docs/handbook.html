PyTorch Core
Tensors · Autograd · Models · Training loop

PyTorch is the foundation everything else is built on. Before loading any model you need to understand how tensors move between devices, how autograd tracks gradients, and how a training loop ties loss, backprop, and optimizer step together. These patterns repeat verbatim inside every Trainer you'll ever use.

🔷 Tensors & Device
import torch

device = "cuda" if torch.cuda.is_available() else "cpu"

x = torch.tensor([[1.0, 2.0]])
x = torch.randn(3, 4)            # normal dist
x = x.to(device)                  # move to GPU
x.reshape(2, -1)  x.squeeze()  x.T
torch.cat([a, b], dim=0)          # concat
x.float()  x.long()  x.numpy()
⚡ Autograd
x = torch.randn(3, requires_grad=True)
loss = (x ** 2).sum()
loss.backward()    # compute grads
x.grad             # dy/dx

# Disable for inference
with torch.no_grad():
    pred = model(x)

optimizer.zero_grad()   # 1. clear
loss.backward()          # 2. grads
optimizer.step()         # 3. update
🧠 nn.Module & Layers
import torch.nn as nn

class Net(nn.Module):
    def __init__(self):
        super().__init__()
        self.net = nn.Sequential(
            nn.Linear(784, 256), nn.ReLU(),
            nn.Dropout(0.2),
            nn.Linear(256, 10))
    def forward(self, x):
        return self.net(x)

model = Net().to(device)
# Also: Conv2d, LSTM, Embedding, LayerNorm
🔁 Training Loop + Save
loss_fn = nn.CrossEntropyLoss()
opt = torch.optim.AdamW(model.parameters(), lr=1e-3)

for epoch in range(epochs):
    model.train()
    for X, y in train_loader:
        X, y = X.to(device), y.to(device)
        loss = loss_fn(model(X), y)
        opt.zero_grad(); loss.backward(); opt.step()
    model.eval()
    with torch.no_grad():
        pass  # validate here

torch.save(model.state_dict(), "model.pt")
model.load_state_dict(torch.load("model.pt"))
⚠️ Always call model.train() before training and model.eval() before validation — Dropout and BatchNorm behave differently in each mode.

HF Datasets
Load · Inspect · Map · Filter · Format for training

The Hugging Face Datasets library gives you a single, memory-mapped interface to thousands of public datasets and your own files. Arrow-backed columns mean map/filter transforms run fast even on datasets too large for RAM. Getting data into the right shape — renaming columns, applying chat templates, setting the format to torch — is typically 80% of a fine-tuning project.

HF Transformers
Pipeline · Tokenizer · AutoModel · Trainer · Push to Hub

Transformers is the model zoo: tokenizers, AutoModel classes, and the Trainer API in one package. The pipeline abstraction lets you call any model in two lines; AutoTokenizer / AutoModelForCausalLM give you full control. The Trainer handles the training loop, gradient accumulation, mixed precision, and checkpointing automatically.

               model="openai/whisper-large-v3")

from transformers import AutoModelForSequenceClassification, AutoTokenizer, TrainingArguments, Trainer, DataCollatorWithPadding

trainer = Trainer(model=model, args=args, train_dataset=ds["train"], eval_dataset=ds["test"],
    processing_class=tok, data_collator=DataCollatorWithPadding(tok))
trainer.train()
trainer.push_to_hub("username/my-model")   # save + push

LoRA & QLoRA Concepts
Parameter-efficient fine-tuning — the theory you need

LoRA (Hu et al., 2021) freezes the original weight matrix W and adds a low-rank bypass ΔW = BA (rank r ≪ d). Only A and B are trained — typically 0.1–1% of total parameters — cutting VRAM by 60-80%. QLoRA (Dettmers et al., 2023) goes further: quantise the frozen base to 4-bit NF4, then apply LoRA on top. These two papers made 70B fine-tuning on a single consumer GPU practical.

🧩 What is LoRA?
Freeze the base model. Inject small rank-r matrices (A and B) into attention layers.

Original weight W stays frozen.
Update: ΔW = A × B (r ≪ d)

Only A and B are trained → <1% of total params.

r (rank) = adapter size. Higher r = more expressiveness, more VRAM.
lora_alpha = scaling factor. Keep = r for simplicity.
rsLoRA (use_rslora=True) scales alpha by √r instead of r — better gradient flow at high ranks.
🔢 QLoRA = LoRA + 4-bit
Base model quantized to 4-bit NF4 (NormalFloat4).
LoRA adapters trained in bf16.

Result:
• 8B model: ~16GB → ~5.4GB
• Enables fine-tuning on single consumer GPU

Trade-off: ~39% slower than full LoRA.

When done, merge adapters back into base for inference — no overhead at runtime.
4-bit training = QLoRA. load_in_4bit=True in from_pretrained.
📊 Pick Your Config
ParamValueEffect
r8–16Standard, balanced
r32–64More expressive, more VRAM
lora_alpha= rNeutral scaling
lora_alpha2× rStronger updates
dropout0Recommended by Unsloth

Target all: q_proj k_proj v_proj o_proj gate_proj up_proj down_proj

Unsloth — Fast SFT Fine-Tuning
2× faster · 60% less VRAM · Full end-to-end workflow

Unsloth re-implements the hot kernels (RoPE, attention, cross-entropy) in Triton and patches them into Hugging Face models at load time — no model changes required. The result is ~2× faster training and ~60% less VRAM versus a plain PEFT/QLoRA setup. It's the go-to choice for supervised fine-tuning on a single GPU with limited memory.

① Load + ② Attach LoRA
from unsloth import FastLanguageModel

model, tokenizer = FastLanguageModel.from_pretrained(
    model_name    = "unsloth/Meta-Llama-3.1-8B-bnb-4bit",
    max_seq_length= 2048,
    load_in_4bit  = True,   # False → 16-bit LoRA
    dtype         = None)

model = FastLanguageModel.get_peft_model(model,
    r=16, lora_alpha=16, lora_dropout=0,
    target_modules=["q_proj","k_proj","v_proj","o_proj",
                    "gate_proj","up_proj","down_proj"],
    use_rslora=True,
    use_gradient_checkpointing="unsloth")
③ Dataset + ④ Train
from unsloth.chat_templates import get_chat_template
from datasets import load_dataset
from trl import SFTTrainer
from transformers import TrainingArguments
from unsloth import is_bfloat16_supported

tokenizer = get_chat_template(tokenizer, chat_template="chatml")
ds = load_dataset("mlabonne/FineTome-100k", split="train")
ds = ds.map(lambda x: {"text": [
    tokenizer.apply_chat_template(m, tokenize=False)
    for m in x["conversations"]]}, batched=True)

trainer = SFTTrainer(model=model, tokenizer=tokenizer,
    train_dataset=ds, dataset_text_field="text",
    max_seq_length=2048, packing=True,
    args=TrainingArguments(output_dir="output",
        num_train_epochs=1, per_device_train_batch_size=8,
        gradient_accumulation_steps=2, learning_rate=3e-4,
        lr_scheduler_type="linear", warmup_steps=10,
        optim="adamw_8bit", weight_decay=0.01,
        fp16=not is_bfloat16_supported(),
        bf16=is_bfloat16_supported(), seed=42))
trainer.train()

Causal LM Fine-Tuning & Continued Pretraining
Raw text training · next-token prediction · domain adaptation

Causal language modelling trains the model to predict the next token from raw text — no labels needed. It's the right approach when you want to adapt the model's knowledge or writing style rather than teach it a specific instruction format. Continued pretraining on domain text (medical, legal, code) shifts the model's priors before you apply SFT on top. DataCollatorForLanguageModeling(mlm=False) auto-constructs the shifted labels from your input tokens.

📖 Causal LM Fine-Tuning — What & When
SFT (instruction) = model learns Q→A pairs with chat template.
Causal LM FT = model learns to continue raw text — next-token prediction on your corpus.

Use causal LM fine-tuning when:
  • You want domain-style text generation (legal, medical, code)
  • Your data is raw documents, not instruction pairs
  • You're doing continued pretraining on a new corpus
  • Building a base model before instruction tuning
Key: labels = input_ids — the model predicts every next token. Loss is computed on all tokens (unlike SFT where you can mask the prompt).
🔁 Causal LM Fine-Tune — Full Example
from transformers import (AutoModelForCausalLM, AutoTokenizer,
    Trainer, TrainingArguments, DataCollatorForLanguageModeling)
from datasets import load_dataset

model_name = "meta-llama/Llama-3.1-8B"   # base, not instruct
tok   = AutoTokenizer.from_pretrained(model_name)
tok.pad_token = tok.eos_token              # required for causal LM
model = AutoModelForCausalLM.from_pretrained(
    model_name, device_map="auto", torch_dtype="auto")

# Load raw text corpus
ds = load_dataset("text", data_files={"train":"corpus.txt"})
# or from Hub: load_dataset("wikitext","wikitext-103-raw-v1")

def tokenize(batch):
    enc = tok(batch["text"], truncation=True,
               max_length=2048, padding="max_length")
    enc["labels"] = enc["input_ids"].copy()  # ← predict every token
    return enc

ds = ds.map(tokenize, batched=True, remove_columns=["text"])

# DataCollator handles labels automatically
collator = DataCollatorForLanguageModeling(
    tokenizer=tok, mlm=False)  # mlm=False → causal (GPT-style)

trainer = Trainer(
    model=model,
    args=TrainingArguments(
        output_dir="./causal-ft",
        num_train_epochs=1,
        per_device_train_batch_size=4,
        gradient_accumulation_steps=8,   # eff. batch = 32
        learning_rate=2e-5,
        lr_scheduler_type="cosine",
        warmup_ratio=0.05,
        fp16=True,
        logging_steps=50,
        save_strategy="epoch",
    ),
    train_dataset=ds["train"],
    data_collator=collator,
)
trainer.train()
model.save_pretrained("./causal-ft")

# Then fine-tune the pretrained model with SFT (instruction data)
Continued pretraining injects domain knowledge. Follow up with SFT instruction tuning on the same domain for best results.
🎯 Train on Responses Only (SFT — mask prompt loss)
# Standard SFT computes loss on BOTH prompt + response.
# train_on_responses_only() masks the prompt — more efficient.
from trl import SFTTrainer
from unsloth.chat_templates import train_on_responses_only

trainer = SFTTrainer(
    model=model, tokenizer=tokenizer,
    train_dataset=dataset,
    dataset_text_field="text",
    max_seq_length=2048, packing=False,
    args=TrainingArguments(...),
)

# Wrap trainer to mask prompt tokens from loss
trainer = train_on_responses_only(
    trainer,
    instruction_part = "<|im_start|>user\n",   # ChatML
    response_part    = "<|im_start|>assistant\n",
)
trainer.train()

# For Llama-3 instruct format:
# instruction_part = "<|start_header_id|>user<|end_header_id|>\n\n"
# response_part    = "<|start_header_id|>assistant<|end_header_id|>\n\n"
Response-only training = model only learns from its own outputs, not from memorising user prompts. Often improves quality.

Fine-Tuning Methods — Full Comparison
SFT · Causal LM · DPO · ORPO · GRPO · Pretraining — know which to reach for

Choosing the wrong training method wastes GPU hours. SFT teaches format; Causal LM teaches domain knowledge; DPO / ORPO align the model to human preferences without a live reward model; GRPO uses verifiable rewards (math answers, code execution) for self-improvement. The table below shows exactly when each method applies and what data it needs.

📊 Method Comparison at a Glance
MethodData formatLoss targetWhen to useTRL class
Continued Pretraining Raw text documents All tokens (CLM) Inject domain knowledge into base model SFTTrainer (no template)
Causal LM FT Raw text / completions All tokens (CLM) Style/domain adaptation, base model training Trainer + DataCollatorForLanguageModeling
SFT (instruction) {instruction, response} pairs All or response-only tokens Teach model to follow instructions SFTTrainer
DPO {prompt, chosen, rejected} triples Preference margin loss Align after SFT — prefer chosen over rejected DPOTrainer
ORPO {prompt, chosen, rejected} triples SFT loss + odds ratio penalty SFT + alignment in one pass, no reference model ORPOTrainer
GRPO Prompts + reward function Group relative policy reward Reasoning / math — reward-based RL (DeepSeek-R1 style) GRPOTrainer
🟩 Causal LM Fine-Tuning
# Train on raw text — no chat template needed.
# DataCollatorForLanguageModeling shifts labels automatically.
# Use when: domain adaptation, style transfer, continued pretraining.
from transformers import (AutoTokenizer, AutoModelForCausalLM,
    DataCollatorForLanguageModeling, Trainer, TrainingArguments)
from datasets import load_dataset

tok = AutoTokenizer.from_pretrained("gpt2")
tok.pad_token = tok.eos_token
model = AutoModelForCausalLM.from_pretrained("gpt2")
model.config.pad_token_id = tok.eos_token_id

# Your domain text — one document per row in "text" column
ds = load_dataset("text", data_files="corpus.txt", split="train")
ds = ds.map(lambda x: tok(x["text"], truncation=True, max_length=512),
          batched=True, remove_columns=["text"])

collator = DataCollatorForLanguageModeling(tok, mlm=False)
# mlm=False → next-token prediction; labels = input_ids shifted by 1

trainer = Trainer(
    model=model,
    args=TrainingArguments(
        output_dir="./clm-out",
        num_train_epochs=3,
        per_device_train_batch_size=4,
        learning_rate=2e-5,
        fp16=torch.cuda.is_available(),
    ),
    train_dataset=ds,
    data_collator=collator,
    processing_class=tok,
)
trainer.train()
Use Causal LM FT to shift the model's knowledge and style before SFT. Run on domain corpus first, then SFT on instruction pairs.
🔵 DPO — Direct Preference Optimization
# Data: {prompt, chosen, rejected}
# {"prompt":"Q:...", "chosen":"good answer", "rejected":"bad answer"}
from trl import DPOTrainer, DPOConfig
from datasets import load_dataset

model_name = "username/my-sft-model"  # start from SFT model
tok   = AutoTokenizer.from_pretrained(model_name)
model = AutoModelForCausalLM.from_pretrained(
    model_name, torch_dtype="auto", device_map="auto")

ds = load_dataset("mlabonne/orpo-dpo-mix-40k", split="train")
# needs columns: prompt, chosen, rejected

trainer = DPOTrainer(
    model=model,
    ref_model=None,              # None = use initial model as ref
    args=DPOConfig(
        output_dir="./dpo-out",
        num_train_epochs=1,
        per_device_train_batch_size=4,
        learning_rate=5e-7,        # very small LR for DPO
        beta=0.1,                  # KL penalty strength
        fp16=True,
    ),
    processing_class=tok,
    train_dataset=ds,
)
trainer.train()
DPO = most common post-SFT alignment step. Run SFT first, then DPO on preference data.
🟢 ORPO — One-Pass SFT + Alignment
# Same data format as DPO but trains SFT + alignment together.
# No separate reference model needed → faster + cheaper.
# NOTE: ORPO lives in trl.experimental.orpo (not top-level trl)
from trl.experimental.orpo import ORPOTrainer, ORPOConfig

model_name = "meta-llama/Llama-3.1-8B"  # start from BASE model
tok   = AutoTokenizer.from_pretrained(model_name)
model = AutoModelForCausalLM.from_pretrained(
    model_name, torch_dtype="auto", device_map="auto")

ds = load_dataset("mlabonne/orpo-dpo-mix-40k", split="train")

trainer = ORPOTrainer(
    model=model,
    args=ORPOConfig(
        output_dir="./orpo-out",
        num_train_epochs=1,
        per_device_train_batch_size=4,
        learning_rate=8e-6,
        beta=0.1,               # odds ratio weight
        max_length=1024,     # max_prompt_length removed in trl 1.x
        fp16=True,
    ),
    processing_class=tok,
    train_dataset=ds,
)
trainer.train()
ORPO skips the SFT step — go straight from base model to aligned model in one training run.
🟠 GRPO — RL from Reward (DeepSeek-R1 style)
# GRPO = model generates multiple responses per prompt,
# scores them with a reward function, updates policy.
# Used for reasoning / math / verifiable tasks.
from trl import GRPOTrainer, GRPOConfig

# Define reward function (returns float per response)
def reward_fn(completions, **kwargs):
    # Example: reward correct math answers
    rewards = []
    for c in completions:
        answer = extract_answer(c)   # your parsing logic
        rewards.append(1.0 if answer == correct_answer else 0.0)
    return rewards

ds = load_dataset("openai/gsm8k", "main", split="train")
# gsm8k has "question" column — rename to "prompt" (required by GRPOTrainer)
ds = ds.map(lambda x: {"prompt": x["question"]}, remove_columns=["question"])

trainer = GRPOTrainer(
    model=model,
    reward_funcs=[reward_fn],   # reward_funcs is a LIST of callables
    args=GRPOConfig(
        output_dir="./grpo-out",
        num_train_epochs=1,
        per_device_train_batch_size=4,
        learning_rate=1e-6,
        num_generations=4,            # must be <= per_device_train_batch_size
        max_completion_length=512,    # renamed from max_new_tokens in trl 1.x
        fp16=True,
    ),
    processing_class=tok,
    train_dataset=ds,
)
trainer.train()
GRPO needs a verifiable reward signal — best for math, code, structured output. Hard to apply to open-ended chat.
📌 Recommended Training Pipeline
For a general assistant:
  1. Start from a strong base model (Llama, Qwen, Mistral)
  2. Optional: Continued pretraining on your domain corpus
  3. SFT on instruction pairs (Unsloth + SFTTrainer)
  4. DPO on preference data to align outputs
For a reasoning / math model:
  1. Start from instruct model
  2. GRPO with verifiable reward (accuracy, format)
For fastest path to aligned model:
  1. Base model → ORPO (SFT + alignment in one shot)
LR guidelines: Pretraining 1e-4 → SFT 3e-4 → DPO 5e-7 → GRPO 1e-6
Always use a lower LR for alignment than for SFT.

AWS SageMaker
Train & deploy HF models in the cloud — full control

SageMaker manages compute provisioning, distributed training, spot interruption recovery, and model artifact storage. You write a standard training script, wrap it in a HuggingFace estimator, and SageMaker handles everything else. It's the right choice when your dataset or model is too large for a local GPU — or when you need reproducible, auditable training runs at scale.

🔧 Setup + Training Script

The Dataset Zoo
PyTorch Dataset → DataLoader → HF Dataset → DataCollator — untangled

Four things called "dataset" and nobody explains how they connect. This is the single biggest source of confusion when coming from general Python/ML into the HuggingFace fine-tuning stack. Here's the complete picture — what each layer does, when you need it, and what the Trainer hides from you.

🔶 PyTorch Dataset
from torch.utils.data import Dataset

class MyDataset(Dataset):
    def __init__(self, texts, tokenizer):
        self.texts = texts
        self.tokenizer = tokenizer

    def __len__(self):
        return len(self.texts)

    def __getitem__(self, idx):
        return self.tokenizer(self.texts[idx])
What: Abstract base class. You subclass it, implement __len__ + __getitem__.
Storage: Row-oriented, in-memory (everything in RAM).
Use when: Custom data sources, non-text data, legacy code.
For LLM fine-tuning: Almost never needed — HF Dataset replaces this.
🔷 HF datasets.Dataset
from datasets import Dataset, load_dataset

ds = load_dataset("json", data_files="data.jsonl")
ds = Dataset.from_dict({"text": ["hi", "bye"]})

# Transform without subclassing
ds = ds.map(tokenize_fn, batched=True)
ds = ds.filter(lambda x: len(x["text"]) > 10)

# Make it act like a PyTorch Dataset
ds.set_format("torch")
What: Column-oriented, Arrow-backed, memory-mapped from disk.
Storage: Doesn't load everything into RAM. 50GB dataset? No problem.
Has: .map(), .filter(), .select() — no subclassing needed.
Key insight: It implements __getitem__ + __len__, so DataLoader and Trainer accept it directly.
🔀 DataLoader
from torch.utils.data import DataLoader

loader = DataLoader(
    dataset,            # any Dataset (PyTorch or HF)
    batch_size=8,
    shuffle=True,
    num_workers=4,
    collate_fn=collator # ← this is where collators plug in
)

for batch in loader:
    outputs = model(**batch)
What: Wraps a Dataset. Handles batching, shuffling, parallel loading.
collate_fn: Takes a list of individual samples → returns one batch dict.
You rarely create one. Trainer builds it internally from your dataset + collator.
📦 DataCollator
from transformers import (
    DataCollatorWithPadding,          # classification
    DataCollatorForLanguageModeling,  # causal LM / MLM
    DataCollatorForSeq2Seq,           # encoder-decoder
)
from trl import DataCollatorForCompletionOnlyLM # SFT

collator = DataCollatorForLanguageModeling(
    tokenizer=tok, mlm=False)   # causal LM
What: A fancy collate_fn. Takes list of examples → returns padded + labeled batch.
Dynamic padding: Pads to longest in batch, not global max (saves compute).
Creates labels: For causal LM, labels = input_ids with -100 on padding.
Key detail: The label shift for next-token prediction happens inside the model, not in the collator.
⚡ How Trainer Wires It All Together
You provide:                          Trainer creates internally:
─────────────                          ──────────────────────────
train_dataset  (HF Dataset)         →  DataLoader(
  +                                        dataset=train_dataset,
data_collator  (e.g. LM collator)   →      collate_fn=data_collator,
  +                                        batch_size=args.per_device_train_batch_size,
TrainingArguments                    →      sampler=RandomSampler,
                                       )

# The Trainer's default collator selection:
# 1. You provide data_collator           → uses that
# 2. You provide tokenizer, no collator  → DataCollatorWithPadding
# 3. Neither                             → default_data_collator (just stacks)

# SFTTrainer goes even further:
trainer = SFTTrainer(
    model="Qwen/Qwen3-0.6B",
    train_dataset=ds,           # just needs a "text" or "messages" column
    args=SFTConfig(output_dir="./out"),
)
# SFTTrainer handles: tokenization → collation → label masking → training
# You never write a collator or DataLoader.
📋 Which Collator For What?
Collator Task What It Does
DataCollatorWithPadding Classification Dynamic padding only. No label manipulation.
DataCollatorForLanguageModeling Causal LM / MLM mlm=False: labels = input_ids, -100 on padding. mlm=True: masks 15% of tokens.
DataCollatorForSeq2Seq Translation, Summarization Pads both input and decoder labels. -100 on label padding.
DataCollatorForCompletionOnlyLM SFT (instruction tuning) Masks prompt tokens with -100. Only completion contributes to loss.
default_data_collator Pre-padded data Just stacks tensors. No padding. Requires uniform sequence lengths.
⚠️ Common Gotchas
1. "I padded in .map() — why do I need a collator?"
You don't need one, but fixed padding wastes compute. A batch of [12, 18, 15]-token sequences pads to 18, not 512. That's the collator's job.

2. "I wrote a PyTorch Dataset subclass"
You almost certainly didn't need to. Dataset.from_dict() or load_dataset() + .map() covers 99% of fine-tuning.

3. "HF Dataset vs PyTorch Dataset — which am I using?"
They're different classes from different libraries. HF datasets.Dataset is NOT a subclass of torch.utils.data.Dataset. It just implements the same interface (duck typing). Both work with DataLoader.

4. "Where does the label shift happen for next-token prediction?"
Not in the collator. The collator sets labels = input_ids. The one-position shift happens inside model.forward(). The model handles its own architecture.

5. "Loss doesn't decrease despite training"
Check labels. If you set labels manually AND use a LM collator, they may conflict. Let the collator handle labels, or don't use one.

PyTorch Module Internals
nn.Module · ModuleList gotcha · Weight surgery · HF head swapping

PyTorch's module system is deceptively simple — until you store layers in a plain Python list and nothing trains. This chapter covers the mechanics that senior developers trip over: how nn.Module discovers parameters, why nn.ModuleList exists, how to freeze/unfreeze layers, and what HuggingFace actually does when you call AutoModelForSequenceClassification.

⚠️ The ModuleList Gotcha — #1 Silent Bug
# WRONG — layers are INVISIBLE to PyTorch
class BrokenNet(nn.Module):
    def __init__(self):
        super().__init__()
        self.layers = [nn.Linear(10, 10)
                        for _ in range(3)]
        # ↑ plain list: .parameters() returns NOTHING
        # Won't train, won't save, won't move to GPU

# CORRECT — use nn.ModuleList
class FixedNet(nn.Module):
    def __init__(self):
        super().__init__()
        self.layers = nn.ModuleList([
            nn.Linear(10, 10) for _ in range(3)
        ])
        # ↑ registered! .parameters() finds all 6 tensors

# Same for dicts: use nn.ModuleDict, not {}
self.heads = nn.ModuleDict({
    "cls": nn.Linear(10, 2),
    "reg": nn.Linear(10, 1),
})
Rule: If it has parameters, it must be an nn.Module attribute — not inside a plain Python list or dict.
🔀 Non-Linear Forward Pass
class ResidualBlock(nn.Module):
    def __init__(self, dim):
        super().__init__()
        self.ff = nn.Sequential(
            nn.Linear(dim, dim * 4),
            nn.GELU(),
            nn.Linear(dim * 4, dim),
        )
        self.norm = nn.LayerNorm(dim)

    def forward(self, x):
        return self.norm(x + self.ff(x))
        # ↑ skip connection: input goes TWO paths

# Multi-head: shared backbone, different task heads
class MultiTaskModel(nn.Module):
    def forward(self, x, task="cls"):
        features = self.backbone(x)  # shared
        if task == "cls":
            return self.classifier(features)
        return self.regressor(features)
forward() is just Python. Skip connections, branches, conditionals, shared layers — all fine. nn.Sequential is a convenience, not a requirement.
🔬 Weight Surgery — Freeze, Modify, Replace
# Freeze a layer
for p in model.layer1.parameters():
    p.requires_grad = False

# Freeze ALL, then unfreeze just the head
for p in model.parameters():
    p.requires_grad = False
for p in model.head.parameters():
    p.requires_grad = True

# Inspect weights
w = model.layer1.weight         # tensor
print(w.shape, w.data.mean())

# Modify weights directly
with torch.no_grad():
    model.layer1.bias.zero_()
    model.layer1.weight.copy_(other_model.layer1.weight)

# Replace a layer entirely
model.head = nn.Linear(768, 10)  # new, trainable

# Save / load weights
torch.save(model.state_dict(), "w.pt")
model.load_state_dict(torch.load("w.pt"))
🔄 HuggingFace Head Swapping
from transformers import (
    AutoModel,
    AutoModelForCausalLM,
    AutoModelForSequenceClassification,
)

# Same "gpt2" backbone, different heads:
base = AutoModel.from_pretrained("gpt2")
#   → GPT2Model (no head, raw hidden states)

causal = AutoModelForCausalLM.from_pretrained("gpt2")
#   → GPT2Model + lm_head (768 → 50257)
#     lm_head = pretrained (came with the model)

clf = AutoModelForSequenceClassification.from_pretrained(
    "gpt2", num_labels=3)
#   → GPT2Model + score (768 → 3)
#     score = RANDOMLY INITIALIZED ← train this!
HF strips the original head and adds a task-specific one. The backbone weights are identical. The new head is random — you must fine-tune it.
📋 AutoModelFor* — Which Class Adds Which Head
Class Head Added Output Shape Task
AutoModel None [batch, seq, hidden] Raw features / embeddings
AutoModelForCausalLM lm_head [batch, seq, vocab] Next token prediction
AutoModelForSequenceClassification score / classifier [batch, num_labels] Sentiment, intent, topic
AutoModelForTokenClassification classifier [batch, seq, num_labels] NER, POS tagging
AutoModelForQuestionAnswering qa_outputs [batch, seq, 2] Extractive QA (start/end)
AutoModelForMaskedLM cls [batch, seq, vocab] Fill-in-the-blank (BERT)
AutoModelForSeq2SeqLM lm_head (decoder) [batch, seq, vocab] Translation, summarization

How to Know If Fine-Tuning Worked
Loss curves · Perplexity · Generation quality · Overfitting detection

Fine-tuning without evaluation is flying blind. You need to check at least three things: is the loss decreasing?, is the model generating better outputs?, and is it overfitting? This section gives you the concrete patterns.

📉 1. Loss Curves
# After trainer.train(), inspect the log history
result = trainer.train()

for entry in trainer.state.log_history:
    if "loss" in entry and "eval_loss" not in entry:
        print(f"step {entry['step']:>4d}  loss={entry['loss']:.4f}")
    if "eval_loss" in entry:
        print(f"epoch {entry['epoch']}  eval_loss={entry['eval_loss']:.4f}")
Train loss should decrease steadily. If eval loss spikes while train loss drops — you're overfitting.
📐 2. Perplexity
import math

# Perplexity = exp(eval_loss)
# Lower = model assigns higher probability to correct tokens
metrics = trainer.evaluate()
ppl = math.exp(metrics["eval_loss"])
print(f"perplexity: {ppl:.2f}")

# Compare before vs after fine-tuning
# baseline_ppl=328 → after_ppl=9 = significant improvement
Perplexity is the standard LM metric. Always compute it before AND after fine-tuning to measure improvement.
🔍 3. Generation Quality Check
# Use the same prompts before and after training
test_prompts = ["LoRA injects", "The learning rate", "GRPO uses"]

for prompt in test_prompts:
    inputs = tok(prompt, return_tensors="pt").to(device)
    with torch.no_grad():
        out = model.generate(**inputs, max_new_tokens=40, temperature=0.7)
    print(tok.decode(out[0], skip_special_tokens=True))

# BEFORE: "LoRA injects a new layer of complexity into the game..."  (generic)
# AFTER:  "LoRA injects low-rank matrices into transformer..."       (domain-relevant)
Automated metrics don't catch everything. Always eyeball generations from a fixed set of test prompts.
⚠️ 4. Overfitting Detection
Symptom: train_loss keeps dropping, but eval_loss starts rising after epoch N.
Cause: Model is memorizing training examples instead of learning patterns.
Fixes:
  • Reduce num_train_epochs (often 1–3 is enough for fine-tuning)
  • Add more training data
  • Increase weight_decay (e.g., 0.01 → 0.1)
  • Use eval_strategy="steps" with small eval_steps to catch the turn early
Always pass an eval_dataset to the trainer. Without it, you have no way to detect overfitting.

Bring Your Own Data
CSV · JSONL · Plain text → trainer-ready datasets

Every trainer expects a specific column layout. This section shows exactly how to get your CSV, JSONL, or plain text files into the right shape — no guessing, just load_dataset() + one .map() call.

📥 Loading Your Files
from datasets import load_dataset

# CSV
ds = load_dataset("csv", data_files="my_data.csv")

# JSONL (one JSON object per line)
ds = load_dataset("json", data_files="my_data.jsonl")

# Plain text (one sample per line)
ds = load_dataset("text", data_files="corpus.txt")

# Multiple files / directory
ds = load_dataset("csv", data_files="data/*.csv")
🔄 Column Mapping
# Your CSV has "question" + "answer" columns
# SFTTrainer needs "prompt" + "completion"

ds = ds.map(lambda x: {
    "prompt": x["question"],
    "completion": x["answer"],
}, remove_columns=["question", "answer"])

# Or just rename if columns already match
ds = ds.rename_columns({
    "instruction": "prompt",
    "output": "completion",
})
Format Cheatsheet — What Each Trainer Expects
Trainer Required Columns Example
Causal LM "text" {"text": "LoRA injects low-rank matrices..."}
SFT "prompt" + "completion"
or "messages"		 {"prompt": "What is LoRA?", "completion": "LoRA adds..."}
DPO / ORPO "prompt" + "chosen" + "rejected" {"prompt": "...", "chosen": "good", "rejected": "bad"}
GRPO "prompt" {"prompt": "What is 2+2?"} (reward from functions)
🧹 Data Hygiene
# Filter short/empty rows
ds = ds.filter(lambda x: len(x["text"]) > 10)

# Remove duplicates
seen = set()
def dedup(x):
    if x["text"] in seen: return False
    seen.add(x["text"]); return True
ds = ds.filter(dedup)

# Train/test split
splits = ds.train_test_split(test_size=0.2, seed=42)

# Save for reuse
ds.save_to_disk("processed_dataset/")
Always split before training. Without an eval set, you can't detect overfitting.

4
SFT on SQL → text
Load sql_to_text_pairs.jsonl as {"prompt": sql, "completion": explanation}.
You can either train a separate model or continue fine-tuning the same model on both tasks (multi-task SFT).
Decision: Single model for both directions or two specialized models? Single is harder but more useful. Try both and compare.
5
Build the RAG baseline
No fine-tuning — just retrieval-augmented generation in memory:
  1. Chunk knowledge_dump.txt + schema into ~200-token passages
  2. Embed with sentence-transformers (all-MiniLM-L6-v2) — stores in a list, no vector DB needed
  3. At query time: embed the question, cosine-similarity top-3 chunks, stuff into prompt
  4. Feed to the same base model (un-fine-tuned GPT-2 / SmolLM / Llama)
This is your control group. The fine-tuned model must beat this to justify the training cost.
6
Evaluate — the honest comparison
Hold out 20% of your text↔SQL pairs as test set. For each test question, generate from:
  (a) Base model (no fine-tuning, no RAG)
  (b) Base model + RAG (retrieved context in prompt)
  (c) Domain-adapted model (Phase 2 only)
  (d) Fully fine-tuned model (Phase 2 + 3 + 4)

Metrics to compare:
  • Perplexity on domain text (lower = better knowledge internalization)
  • SQL exact match — does the generated SQL match the gold query?
  • SQL execution match — does it return the same results? (harder but more fair)
  • Explanation quality — human judgment: is the SQL→text explanation correct?
  • Latency — fine-tuned model generates in one pass; RAG needs embed + retrieve + generate
7
Ship it — submit what you built
Push your repo to GitHub. Your submission should include:
  • Training scripts for each phase (causal LM, SFT text→SQL, SFT SQL→text)
  • RAG baseline script
  • Evaluation script with comparison table
  • A short write-up: what worked, what didn't, which model won, fine-tune vs RAG verdict
  • Link to your fine-tuned model on HuggingFace Hub (optional but encouraged)
Submit: Open a PR to anisiraj/llm_kickstart_repo with your results, or share the link to your own repo.

When fine-tuning is worth it and when it isn't
No shortcuts. The point of this exercise is the journey, not the destination. A small model will not produce perfect SQL — that's expected. What matters is: did the fine-tuned model produce better SQL than the base model? Did it beat RAG? Where did it fail? Your write-up is the most valuable part.

Why two virtual environments?

Unsloth hard-pins trl<0.9.0 in its dependencies. The DPO, ORPO, and GRPO trainers require trl≥1.0 — a completely different API with renamed parameters (max_completion_length, processing_class, etc.) and new trainer classes. These two constraints are mutually exclusive: pip cannot satisfy both in the same environment, and installing one silently downgrades or breaks the other.

The split:
  .venv    → Unsloth + trl 0.24 + SFT  (scripts 01–04, 08–11)
  .venv-rl → trl 1.2 + DPO / ORPO / GRPO  (scripts 05–07)
