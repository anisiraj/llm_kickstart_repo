📐 LLM Evaluation Metrics — what they mean, the code, and when each one lies

You can't improve what you mis-measure. Each metric answers a different question; the classic mistake is scoring an instruction model with a metric that punishes its format. Pick the metric that matches the task — and report relative change on small data, never absolute leaderboard scores.

① Perplexity — did training fit the text?
import torch
def perplexity(model, tok, text):
    ids = tok(text, return_tensors="pt").input_ids.to(model.device)
    with torch.no_grad():
        loss = model(ids, labels=ids).loss   # mean CE over tokens
    return torch.exp(loss).item()                # PPL = e^loss
PPL = exp(cross-entropy) — "how many tokens is the model effectively choosing between." Lower = less surprised. Domain PPL (on raw text) judges CPT; completion PPL (mask the prompt, score the answer) judges SFT. Only comparable on the same text + tokenizer. Don't compare PPL across models with different vocabularies.
② ⚠ The format trap — when PPL lies
An instruction-tuned model scored on plain text looks worse (higher PPL) than a base model — not because it's worse, but because it "wants" chat tokens. SFT can even raise domain PPL while drastically lowering completion PPL. Rule: never rank a base-vs-instruct (or pre-vs-post-SFT) decision on a single perplexity number. Cross-check with a generation-based metric (recall/ROUGE/BERTScore) that doesn't care about format. Real case-study example: MiniCPM5-1B completion PPL 107.7→3.6 (great) while domain PPL rose 24.8→34.9 — the two losses pull opposite ways.
③ Keyword recall / token-F1 — format-robust
def keyword_recall(gold, gen):
    import re
    g = set(re.findall(r"\w+", gold.lower()))
    h = set(re.findall(r"\w+", gen.lower()))
    return len(g & h) / max(len(g), 1)   # fraction of gold words present
Generate an answer, measure how much of the gold answer's content it actually produced. Format-robust: it won't punish the model for chat tokens or phrasing, so it's the honest tie-breaker when perplexity is ambiguous. Cheap + interpretable. For a stricter version use token-level F1 (precision×recall) so verbosity is penalised too.
④ ROUGE & BLEU — n-gram overlap
import evaluate
rouge = evaluate.load("rouge")
rouge.compute(predictions=preds, references=refs)
# {'rouge1':.., 'rouge2':.., 'rougeL':..}

bleu = evaluate.load("bleu")      # precision-oriented (MT)
ROUGE = recall of overlapping n-grams (summarisation, QA). ROUGE-L = longest common subsequence. BLEU = precision of n-grams (translation). Fast, reference-based. Surface-level: a correct paraphrase with different words scores low. Good for structured/templated outputs, weak for open-ended ones.
⑤ BERTScore — semantic similarity
import evaluate
bs = evaluate.load("bertscore")
bs.compute(predictions=preds, references=refs, lang="en")
# P/R/F1 from contextual embedding cosine similarity
Embeds both texts with a pretrained encoder and matches by cosine similarity — so "fast" ≈ "quick" scores high even with zero word overlap. Captures meaning ROUGE/BLEU miss. Heavier (loads a model); score scale isn't 0–1-intuitive — use it for relative comparisons, not an absolute bar.
⑥ Exact match & accuracy — structured tasks
def exact_match(gold, gen):
    return gold.strip().lower() == gen.strip().lower()

# multiple-choice: compare predicted letter to key
acc = sum(p==k for p,k in zip(preds, keys)) / len(keys)
% of outputs that exactly equal the reference. The right metric for classification, multiple-choice, JSON-field extraction — anything with one correct string. Often normalised (lowercase, strip, articles). Brutal for free text: "Paris." ≠ "Paris" fails EM. Reserve for genuinely closed outputs.
⑦ pass@k — functional correctness (code)
# Generate n≥k samples/problem, c = # that pass unit tests
import numpy as np
def pass_at_k(n, c, k):
    if n - c < k: return 1.0
    return 1.0 - np.prod(1.0 - k/np.arange(n-c+1, n+1))
For code/agents: a generation is "correct" iff it passes the tests. pass@k = P(at least one of k samples works), unbiased estimator from n samples (HumanEval). Measures behaviour, not text overlap. Tooling: bigcode-evaluation-harness (HumanEval/MBPP). Run generated code sandboxed.

EleutherAI's harness: 60+ academic benchmarks (MMLU, ARC, HellaSwag, GSM8K, TruthfulQA) with consistent, comparable scoring. The standard way to report "how capable" a model is. Great for capability regressions (did fine-tuning hurt general skill?); not a substitute for your task's own metric.

⑩ LLM-as-judge — open-ended quality
# Ask a strong model to score on a rubric (1–5): correctness,
# conciseness, faithfulness. Use pairwise A/B for less bias.
judge("Rate 1-5 for factual correctness:\nQ:..\nGold:..\nAns:..")
When there's no single right string (style, helpfulness), a rubric-driven judge correlates better with humans than n-gram metrics. Average over many items. Biased toward verbosity/its own style; pin the rubric, randomise A/B order, and spot-check against humans. Never the only metric.
